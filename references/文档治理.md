## D00 先决定是否进入开发读取链

判断标准：这份内容是否会改变Agent当前的实现、验证或操作决定？先筛选材料用途，再设计懒加载路径。可寻址不是收录理由；只有文件链接不会自动加载全文，但多余指针仍增加检索和过时信息的风险。

| 材料 | 默认处理 |
| :-- | :-- |
| 执行约定、当前任务 | 保留薄入口，只携带每次确实需要的信息 |
| 现行需求、数据约束、页面、架构 | 按明确任务条件进入开发索引 |
| 当前环境、构建或部署操作 | 按相关操作进入，命令维护一处 |
| 已运行结果、失败及设备记录 | 作为历史证据，当前任务需要时直达对应章节 |
| 项目介绍、商业交流、采购比较、用户说明 | 保留面向人的入口；只有用户指定用途或本项确需核对时读取 |
| 原型总结、旧交接、原始调研 | 退出常规开发索引；指定快照或确需追溯时再读 |
| 阶段性覆盖核对／差异报告 | 仅作为该分析任务入口；收束后归档结果，独有规则和待办写回所属专题 |

移出索引不等于删除文件、禁止用户读取或加入.gitignore。保留需要的历史与人类材料，不为了治理再建立一套必须遍历的“排除文档索引”。排查重复时，先确认独有约束已在权威来源，再移除过期入口。

## D01 薄入口的分工

先看项目已有入口，再决定要改什么。常用的三种分工如下，文件名可以沿用项目习惯。

| 入口 | 常见文件 | 放什么 |
| :-- | :-- | :-- |
| 协作入口 | AGENTS.md | 从哪里开始，怎样执行，遇到什么情况再读下一份 |
| 设计索引 | docs 下的 README.md | 任务对应的专题、章节或编号 |
| 进度入口 | 项目指定的计划文件、Issue 或看板 | 当前工作项、任务状态和下一步 |

这三种入口是职责分工，可以合并或映射到项目已有工具。入口只带当前路径与必要约定；项目背景、采购过程和旧阶段摘要按任务另读。AGENTS.md保留必要的执行与恢复约定，专题归属和触发条件集中在开发索引；进度入口指向项目指定的状态来源。

索引写清“做什么事时，去哪个文件读哪一段”。例如“涉及事务时，读数据库设计的事务章节”。只列文件名，agent 还得猜什么时候该读。经常漏读某项规则时，先检查入口有没有说清触发条件。

模块可以有自己的 README，写模块内的方案和边界；业务规则仍指向全项目的对应专题，进度仍回到项目指定的状态来源。

## D02 八类规则的唯一写入点

先给已有内容分工，再考虑拆文件。下面的文件名只是例子，小项目可以在同一文件里分章节，不必凑齐八份文档。

| 类别 | 在这里修改 | 常见位置 |
| :-- | :-- | :-- |
| 1. 业务行为与验收 | 用户能观察到的行为、业务边界、验收目标和业务未决 | 需求专题 |
| 2. 数据与事务 | 数据结构、存储约束、并发和事务边界 | 数据库专题 |
| 3. 页面操作与展示 | 操作、布局、导航和页面状态 | 各端页面专题 |
| 4. 共同视觉 | 色彩、字体、间距、共用组件和状态语义 | 风格专题 |
| 5. 架构与技术取舍 | 模块职责、组件边界、选择理由及替代方案 | 架构专题或 ADR |
| 6. 定位与商业决定 | 用户定位、产品范围、定价状态和商业选择 | 项目决策 |
| 7. 开发状态 | 工作队列、当前任务、实现差异和技术暂缓项 | 项目指定的状态来源 |
| 8. 环境与验证证据 | 实际环境、常用命令、构建或设备验证的记录及限制 | 开发环境或证据专题 |

协作流程集中在项目已有的协作约定中，AGENTS.md是常见载体。状态来源可以是计划文件、Issue 或看板，同一项进度只在指定位置更新，其他页面给链接。术语需要统一时，用词汇表给出定义，专题引用词条。

采用 ADR 时，同一技术决定在 ADR 和架构正文之间选一处维护，另一处给编号引用。写清为什么这样选、重要方案为什么被放弃，完整讨论留给历史记录。

目标行为查设计；实际行为查代码、生成契约和运行证据。两者有差异就记进当前工作项，按用户要求处理。

接口契约能从实现生成时，沿用生成方式，其余文档引用它。配置和脚本中随手能查到的参数，给查询入口即可；难从代码看出的约定和理由才需要另写。

## D03 可寻址与引用

经常被引用的内容要有稳定编号。例如 F 是功能、A 是验收、M／W 是端侧页面、ADR 是决定。已有编号就接着用，确实需要跨文档引用时再加新编号。

引用写成“文件路径＋章节标题或编号”。临时行号可以帮助定位，但章节挪动后，编号仍应能找到原来的规则。调整标题或位置时，检查受影响的引用，需要时保留旧编号到新位置的对应关系。

一段规则要放完整：定义、做法和必要例外放在一起，让读者只打开这一段也能理解。功能涉及哪些页面、表和验收，可以用覆盖表列关系，表里只写对应关系。

拆文件看的是读取分支。有独立用途的部分可以拆出；同一任务总要连着读的内容放在一起，省得来回找。

当前环境与历史证据混排时，按用途分离；当前操作只保留实际在用入口，证据保留原日期、范围和失败。迁移后修正维护中的相对引用，旧快照可用原锚点转到指定证据，不批量重写历史。

例如，页面专题写“退款行为见需求 F12，事务见数据库的订单事务章节”，本节只说明退款按钮、输入和反馈。

## D04 读取路径与扩大条件

先从任务里找到业务对象、工作项或页面编号，在索引中确定专题，再搜索对应标题。可用时优先用 rg，先找相关目录和标题，随后读取需要的段落。

读到能判断当前动作、约束和完成条件时就开始工作。跨实体写入、共用规则、相关验收或口径冲突，需要沿引用补读；新证据影响判断时，再回到对应来源。

已经读过、没变且还记得清楚的内容直接复用。相关文件改过、对话压缩后记不清细节，或者出现冲突时，重读所涉部分。

按需读取能少带入无关内容，已经进入上下文的文字不会因此消失。

## D05 维护现行结论

先确定规则归哪份文档，再改原结论，最后检查引用和实现差异。分清用户已有改动与本次修改，保留用户的内容。

正文留下当前结论、必要理由和重要待定项。演化过程通过项目已有版本记录、ADR 或证据引用追溯。原始访谈、样本、采集资料和历史验证记录保留原貌。

维护文档顶部写实际编辑时间，沿用项目时区，精确到分钟。历史证据用当时的日期；更新文档不等于重新验证了里面所有事实。

普通讨论何时落盘按项目约定。改变范围、接口、事务或授权的决定，以及用户明确要求记录的内容，及时写回。使用说明、发布和恢复文档跟着实际流程写，有了能用的流程再补说明。

## D06 三种反模式

| 反模式 | 常见表现 | 怎么改 |
| :-- | :-- | :-- |
| 证据日志膨胀 | 每轮都追加整段命令和输出，反复记录“又通过一次” | 常用命令留一份，证据写日期、范围、结果和限制。长输出按排查需要保存，正文给引用，历史记录保留原日期 |
| 状态层自重复 | README、设计、契约和几个状态文件都在写已完成与下一步；总表和任务卡又抄一遍 | 复用项目指定的状态来源，其他位置给引用。概览只写简短结论，工作项保留细节，完成项留结果和证据入口 |
| 规则否定化 | 不断追加“不要”“禁止”，读完却不知道该怎么做 | 改成触发条件、应做动作和完成条件。权限、隐私及破坏性操作的硬边界保留，同时写清正确动作 |

修改相关内容时顺手检查这三类问题，发现哪里有问题就改哪里。

## D07 新项目入口示例

用户要求初始化规范，或者已有入口确实不够用时，再按真实目录调整这份骨架。尖括号里的内容要换成项目实际配置。

```markdown
# 项目协作约定

更新时间：<实际编辑时间>

## 读取入口

先读本文件和 <设计索引>。开始、收尾或恢复任务时，从 <状态来源> 查看当前进度、相关工作项和下一步。
按索引找专题标题或编号，发现依赖或冲突再扩大读取。

## 规则归属

八类规则的修改位置见 <设计索引的权威来源表>。规则只改所属专题，其他位置引用章节或编号。
执行约定在本文件维护，业务说明留在专题。

## 任务与状态

本次授权和当前任务沿用 <状态来源>，分开记录需求状态、实现状态、验证结果和遗留差异。
范围清楚后执行；收尾按 <本项目验证约定> 检查并更新文档。已有提交授权且项目要求时，再按约定提交。
队列里的其他工作等用户授权后再做。

## 换对话

用户要求换对话或生成交接时，先更新 <状态来源> 和重要决定，再把快照保存到 <交接位置>。
记下进度、设计思路、未提交改动、阻塞和下一步，规则及证据用引用。
回复中写明下一轮建议授权范围，并直接贴出可复制的开场提示。恢复工作时只读指定交接，再核对现行文档。
```

索引指向实际存在的文件或章节。项目很小时，同一文件中的不同章节也能分担这些职责。

## D08 完成检查

检查入口是否只收有开发决策价值的材料；被移出的文件仍能按其实际用途找到。当前状态应尊重最新文件和用户决定，不从旧交接恢复已经改变的顺序。

从这次任务的入口走一遍：相关章节找不找得到，规则有没有重复维护，编号与引用对不对，进度能不能回到项目指定的状态来源。

检查本次差异和受影响的引用即可。用户需要统计读取次数或 token 时，再按实际测量记录；先确认读到的是正确规则。
