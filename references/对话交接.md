## H01 触发与前置动作

用户要求“新开对话”“生成交接”或“准备下一轮接着做”时生成交接。完成一个工作项、询问上下文或讨论交接方式时，先继续眼前工作，需要时给出换对话建议。

下一轮做什么，已有安排就沿用；还没安排时，按[任务规划](会话与状态.md#s01-工作项与对话分别计数)给出建议范围。只有续作对象确实不清楚时才问用户。

保存交接前，依次处理：

1. 把本轮重要决定、规则变化和必要理由写回对应专题。
2. 在项目指定的状态来源更新当前进度、阻塞和下一步，保留原编号及真实完成情况。沿用已有计划文件、Issue 或看板。
3. 检查工作目录及已有改动；项目使用Git时再核对Git差异，分清已有成果、本次未提交改动及用户修改。执行中的命令和事务先处理到安全状态；需要保留的运行进程写清原因。
4. 已有提交授权且项目要求时，按约定提交已完成成果；否则保留当前改动并写清状态。做了一半的内容按进行中交接。
5. 保存快照，引用更新后的文档。下一轮建议范围可以留在快照里，后续进度仍只更新指定的状态来源。

## H02 保存位置与命名

采用项目已规定的目录、时区和命名方式，配置只在协作约定维护一处。

项目没有约定时，可用 docs/handoff；已有其他合适位置就复用。读取实际生成时间，文件名用 YYYY-MM-DD-HHmm-主题.md，顶部写“更新时间：YYYY-MM-DD HH:mm”。时区跟随项目，项目没配置就用用户当前时区，并在文件里注明。

目录缺失时创建；同一分钟重名就追加序号，保留旧快照。历史材料用原日期。

密钥、密码、令牌和真实个人资料不写进交接。需要引用私有证据时，只给必要的定位信息。

## H03 快照需要保留什么

| 内容 | 写什么 |
| :-- | :-- |
| 当前状态 | 项目目录、工作项、授权范围，当前停在规划、实现、验证还是收尾 |
| 本轮已完成 | 简短结果、提交标题或成果路径、验证证据入口 |
| 重要决定与设计思路 | 结论、理由、仍有效的原则、重要否决及对应章节 |
| 阻塞和未完成 | 遗留差异、失败、未运行部分和待决定点 |
| 未提交现场 | 相关文件、改动归属、进行中的动作及要保留的用户内容 |
| 下一步 | 具体动作、完成条件、下一轮建议授权范围和需要用户决定的地方 |
| 必要读取入口 | 协作入口、索引、指定状态来源，以及这项工作要读的章节或编号 |
| 建议技能 | 下一步确实用得上的已知技能与使用理由，没有就省略 |
| 开场提示 | 项目实际路径、下一轮工作范围、交接路径和执行边界 |

交接只带恢复当前工作所必需的差量：独有决定及理由、未提交现场、阻塞、下一动作和精确引用。已有规格、命令、环境路径与完整采样表用引用，不再复制一遍；只有无法从引用恢复的关键信息才在快照展开。不要把交接变成第二套需求、环境或进度文档。

快照中的状态有明确时间点。保存后不再跟着项目进度修改这份快照，后续变化写回指定的状态来源。

## H04 可复用模板

生成时换成真实内容，删掉用不上的段落。

```markdown

更新时间：<实际生成时间>
时区：<项目或用户时区>

## 当前现场

- 项目：<实际工作目录>
- 当前工作项：<编号、目标和真实状态>
- 本次授权：<范围和必要边界>
- 当前状态入口：<计划文件及章节，或对应 Issue／看板链接>

## 本轮已完成

<结果、提交标题或成果路径；验证范围及证据引用>

## 重要决定与设计思路

<结论、理由、原则与重要否决；引用对应章节>

## 阻塞和未完成

<未实现部分、失败或未运行部分、待决定点>

## 未提交现场

<文件和改动归属；用户内容；需要保留的进程，或明确没有本次未提交改动>

## 下一步与建议范围

<选择理由；各项的名称、顺序和完成条件；需要先解决的问题>

## 必要读取

## 建议技能

<确实适用的已知技能与理由；没有就省略本节>

## 可复制开场提示

```

## H05 新对话恢复顺序

1. 到正确的项目目录，读协作入口和设计索引。
2. 从项目指定的状态来源读取当前进度和相关工作项。
3. 读用户指定的这份交接。文件缺失时先看现行文档，确实缺少续作所需事实再问。
4. 按本次任务补读规则、决定及证据章节，核对当前改动和实现。
5. 简短说明接下来做什么、做到哪里，继续已授权工作。

用户没指定交接时，先从当前状态来源和代码恢复。需要某份旧现场时再找对应快照，历史交接按需读取。

有冲突时，用户本次指令决定目标和授权，现行专题说明规则，代码、生成契约和证据说明实际实现，项目指定的状态来源记录进度。交接日期较新也仍是一份快照。

跨对话继续沿用原工作项编号和未完成状态。用户只要求恢复并说明状态时，先交付状态说明。

## H06 交接完成检查

检查文件是否存在，路径和章节是否可用，重要决定有没有写回专题，未提交及未完成内容是否准确。

最后检查回复：交接文件能点开，建议范围已写明，开场提示已经完整贴出，且与交接文档一致。检查文档即可，生成交接不增加业务测试。

## H07 交接后直接在回复里给开场提示

交接保存后，最终回复同时给出交接文件链接、下一轮建议授权范围和一个可以直接复制的 text 代码块。用户在回复框就能复制整段提示，无需先打开文件。

范围按[S01](会话与状态.md#s01-工作项与对话分别计数)选择。回复里单独写“下一轮对话建议授权工作范围是【实际范围】”，后面用一句话解释为什么选这些项。没有现成工作队列时，先列清下一步；规划尚无法完成就写明缺什么，不填虚构编号。

代码块用下面的格式，换成真实路径、工作项及范围：

```text
项目：<实际项目目录>。
使用 $dd-docs-manage，本轮授权工作范围为【<实际工作项范围或逐项列表>】，按 <名称和顺序> 推进。
先读项目协作入口、设计索引和指定状态来源，再读这份交接：<实际交接路径>。
按任务补读对应章节，保留交接中标明的用户改动。每项按项目约定验证、更新状态并收尾；已有提交授权且项目要求时，再按约定提交。
```

同一段提示同时写入交接文档和最终回复，两处的路径、范围保持一致，实际生成时不能留下占位符。

这段文字是给用户采用的开场草稿。用户把它作为新消息发出后，才成为下一轮授权；当前对话按已有授权执行。用户已经定好范围时，提示中直接沿用。

生成交接后，由用户决定何时开新对话。创建或分叉聊天另按用户要求办理。
