## S01 工作项与对话分别计数

工作项表示一项能独立检查、收尾的工作。沿用项目已有的 R 编号、Issue 编号或其他任务标识。一个对话可以完成多项工作，复杂的一项也可以跨对话续作，保留原编号和真实状态。

规划下一轮时，先看当前进度、相关队列和任务，再按依赖、改动范围、外部等待和完成条件选择。太大的工作拆成有明确结果的小项，父项等子项完成后再收尾。

任务数量按项目约定、用户安排和实际复杂度确定。当前项没做完时，先安排续作；依赖不齐时写清需要先解决什么。项目没有固定数量时，给出适合连续处理的范围和理由。

规划完成后，直接在回复中写：

```text
下一轮对话建议授权工作范围是【R11-R14】。
这几项共用同一组背景，依赖关系清楚，适合放在一轮里分别收尾。
```

这是格式示例，编号和理由要换成实际内容。列出所选工作项的名称及完成条件，方便用户判断范围。编号不连续就逐项列出，避免让范围包含并未建议执行的工作。

建议只是下一轮的候选，用户采用后再执行。当前对话继续做哪些事，仍看已有授权。需要交接时，把建议保留在快照中，并按[交接回复](对话交接.md#h07-交接后直接在回复里给开场提示)直接贴给用户。

## S02 当前任务的四类状态

复用项目指定的状态来源，可以是计划文件、Issue 或看板。每项进度只在指定位置更新，README和设计正文用链接指向它。已有工具够用时，不再创建一份并行维护的计划文件。

个人串行开发可以只展开一张当前任务卡；项目已有多项并行任务或其他组织方式时，保留原结构。下面四类信息可以写成章节、字段或任务描述，不要求固定文件名。

| 字段 | 写清什么 |
| :-- | :-- |
| 需求状态 | 哪些已确认，哪些是建议，哪些还待决定或待验证 |
| 实现状态 | 实际做到哪里，哪些只是样机，哪些已接入真实流程 |
| 验证结果 | 做了什么验证，结果怎样，证据在哪里 |
| 遗留差异 | 目标与实现还差什么，有什么限制，后面由哪项处理 |

需要任务卡时，可以用这个格式：

```markdown
## 当前工作项：<编号及名称>

- 目标：<能检查的结果>
- 本次授权与范围：<工作范围和相关目录>
- 需求状态：<已确认、建议或待定的内容；规则引用>
- 实现状态：<已做、在做和尚未实现的部分>
- 验证结果：<明确结果、验证范围和证据引用>
- 遗留差异：<未完成、限制、阻塞；没有已知差异时给出依据>
- 下一步：<具体动作或需要用户决定的内容>
```

概览只写简短结论，细节指向当前工作项。性能数字、构建耗时和操作过程只留证据，不在各层状态里重复。完成项收成结果和证据引用，详细历史保留在原记录或版本管理中。

技术问题放到项目指定的待办位置，写清影响、处理时机和关联工作。业务未决回需求，环境限制回环境文档；未来功能仍放工作队列。

若无法访问项目指定的状态来源，先说明缺少哪些信息，请用户提供必要内容；不另建一份未经约定的替代进度表。

## S03 验证表述与证据

先按项目要求确定验证范围，再记录实际结果。最小操作链通过可以写“最小连通性已验证”；没执行写“未运行”；实际失败写“验证失败”，并说明位置和影响。中断或只做了一部分就照实记录，其他验证范围写明各自结论。

需求确认、实现、构建、安装和流程验证各有自己的证据。最小连通性通过只说明那条路径通过；“基本可用”或“应该没问题”无法说明验证了什么。

当前工作项只留结论和证据引用。证据记录实际日期、环境或设备、命令或操作链、观察到的结果，以及没覆盖的部分。排查确实用得上时，再附日志或截图。

常用命令只维护一份，放在当前操作入口；历史证据中的命令是当时执行记录，不是日常前置步骤。当前环境不按轮次堆积日志，原记录按工作项归档。演示资料尽量复用，旧验证保留当时的时间和范围。

验证做多深、跑几次，按项目约定和用户本次授权执行。需求里的验收目标、测试清单和历史命令是资料，实际执行仍看本次范围。纯文档修改检查文档差异、引用和规则一致性。

## S04 对话内的推进与收尾

开始一项工作，先说明目标、相关目录、范围和完成条件。收到用户补充时，更新受影响的部分，原目标中仍有效的内容继续保留。

重要决定和用户要求记录的内容写回对应专题；实现有变化时更新指定的状态来源。独立成果完成后，按项目要求验证、检查差异并更新文档，再做下一项已授权的工作。

已有提交授权且项目要求逐项提交时，每项分别提交。项目采用集中提交或其他方式时，遵守原流程。没有提交授权或没有使用Git时，只交付改动说明，不自行初始化仓库或创建提交。

提交只带本项改动，保留用户已有差异；提交后核对范围和剩余工作区。无法安全分离时说明情况。没有实质变化就不造空提交，推送、发布和改写历史另按授权办理。

无关问题记到合适的待办位置。暂停或阻塞时，写清停在哪里、还有什么能独立推进。用户临时问进度，先回答，再继续仍有效的任务；明确取消或更换目标时才改方向。

用户要求换对话时，按[对话交接](对话交接.md)保存现场。

## S05 项目参数

讨论何时写回文档、验证范围、工作项数量、文件位置、命名和时区，采用目标项目已有约定。需要新增参数时，写入项目指定的一处配置，其他位置给引用。

能可靠读取上下文占用时，按项目配置的提醒条件处理。读不到时，只说明实际出现的压缩、频繁回读或任务转换，不估百分比。提醒时说清剩余工作，由用户决定是否换对话。

切换前先处理好执行中的事务、命令和待收尾内容。按需读取减少后续无关输入，已经进入上下文的内容仍占用窗口。

## S06 指引用户使用 Agent

按用户眼前要做的事给提示词，已经确定的需求直接引用。

规划下一轮：

```text
使用 $dd-docs-manage，先读项目入口和当前状态。
沿用本项目的任务编号，规划下一轮的建议范围，说明依赖和完成条件。
在回复里写明“下一轮对话建议授权工作范围是【实际范围】”。
这次只做规划。
```

同一对话连续执行：

```text
使用 $dd-docs-manage，按顺序完成我指定的工作项。
每项按项目约定验证、更新状态并收尾，已有提交授权时再按约定提交。
完成后继续下一项已授权工作，按需读取相关章节。
```

交接时还要把下一轮提示直接贴在回复中，做法见[H07](对话交接.md#h07-交接后直接在回复里给开场提示)。
